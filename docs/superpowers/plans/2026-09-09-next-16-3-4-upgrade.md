# next 16.2.10 → 16.3.4, and the CI comment that justified not blocking

Issue **#539**, sub-issue of **#531**. Measured 2026-09-09 in a worktree branched
from `origin/main` at `a331b2ea`.

## What the issue got right, and the two things it got wrong

The issue's core claim holds exactly: `next` and `eslint-config-next` were pinned
at `16.2.10`, `npm audit` names `{ "name": "next", "version": "16.3.4",
"isSemVerMajor": false }` as the fix, and `16.3.4` is npm's `latest`. It is a
patch, not a major.

Two things in it do not survive re-derivation.

**1. The `>=16.0.0 <16.2.11` band holds nine advisories, not seven.** Four high
(SSRF in rewrites, SSRF in Server Actions on custom servers, DoS in App Router
using Server Actions, middleware/proxy bypass) and five moderate (two
cache-confusion entries, an unbounded Edge Server Action payload, a DoS in the
Image Optimization API using SVGs, and the Server-Function-endpoint disclosure).
The "four rated high" half is right; the total is not.

**2. The reachability table's middleware row is false.** It reads "**No
middleware file exists**" and re-derives with `ls src/middleware.ts
middleware.ts`. Next 16 renamed `middleware.ts` to `proxy.ts`, and **`src/proxy.ts`
exists** — the build output names it (`ƒ Proxy (Middleware)`). The command was
checking a filename this version of Next no longer uses, so the row is an
artefact of the probe, not a fact about the repo.

That row matters because `src/proxy.ts` is not incidental: it is the
unauthenticated-request redirect for `/students`, `/inbox`, `/settings`,
`/class` and `/bookings`. GHSA-6gpp-xcg3-4w24's precondition is therefore
**present**, where the issue recorded it as absent.

Its consequence is nevertheless bounded, and the PR body should say so rather
than inherit the advisory's title as a severity. The proxy is a redirect
convenience over checks that run independently behind it:
`src/app/(teacher)/layout.tsx` calls `getSession()` and redirects to `/login`
itself, and the pages under it call `requireTeacherSession()`. A proxy bypass
skips a pre-render redirect; it does not reach teacher data.

## What the issue left open, now closed

The issue flagged one thing as unestablished: whether GHSA-2xp9-vwfh-vxw4 (the
AVIF RCE in the Image Optimization API) is reachable through `/_next/image`,
which Next serves whether or not the app imports `next/image`.

Measured against the running 16.2.10 server, `/_next/image` **is** a live route —
a nonexistent `/_next/*` path returns 404 while `/_next/image` returns a
route-specific 400 — but both of its input paths are closed:

| Probe | Response |
|---|---|
| `url=https%3A%2F%2Fexample.com%2Fa.png` | `400` — `"url" parameter is not allowed` (no `images.remotePatterns`) |
| `url=%2Ffavicon.ico` | `400` — `The requested resource isn't a valid image.` |

Local paths reach the optimizer, but **there is no `public/` directory in this
repo at all** (`ls -la public` → no such file or directory; `ci.yml`'s start
step already guards it with `[ -d public ]`). The advisory needs an AVIF file to
flow through the optimizer, and on this configuration nothing can. Not an
emergency, confirmed by measurement rather than assumed.

## What the upgrade actually moves

`npm install next@16.3.4 eslint-config-next@16.3.4 --save-exact` changes
`package.json` (2 pins) and `package-lock.json`. It closes three packages, not
one, because `next`'s audit entry carries `via: postcss` and `via: sharp` and
both name `next@16.3.4` as their own fix:

| Package | Before | After | Advisory range | Now clean |
|---|---|---|---|---|
| `next` | 16.2.10 | 16.3.4 | `9.3.4-canary.0 - 16.3.2` | yes |
| `postcss` | 8.5.19 | 8.5.23 | `<=8.5.22` | yes |
| `sharp` | 0.34.5 | 0.35.4 | `<=0.35.4-rc.0` | yes |

Both before-versions are read out of `main`'s committed lockfile, not out of the
advisory's range bound — a distinction worth stating because the first draft of
this plan carried `8.5.22` and `0.35.3`, which are the range's edge and a guess
respectively, neither of them a version this repo ever installed. `sharp` moves
a **minor**, not a patch (0.34 → 0.35); it is a native binary dependency, and it
is pulled only through `next`, which nothing in `src/` exercises.

Audit totals, whole tree: **15 → 12** (`{moderate 5, high 9, critical 1}` →
`{moderate 5, high 7, critical 0}`). Production-only (`--omit=dev`): **8 → 5**
(`{moderate 1, high 6, critical 1}` → `{moderate 1, high 4, critical 0}`).
`next` disappears from `npm audit --json`'s `vulnerabilities` object entirely,
which is issue #539's acceptance criterion stated literally.

## Scope: what this PR deliberately does not do

Seven of the twelve remaining advisories carry `fixAvailable: true` — they are
transitive-only and a non-major `npm audit fix` would move them. This PR does
not run it. The acceptance criterion names the standalone build as the thing to
watch across a two-minor framework bump; folding a `vitest` bump into the same
diff means a red suite cannot be attributed. Filed as a leaf under #531 instead.

The three `prisma`-rooted entries (`prisma`, `@prisma/config`, `deepmerge-ts`)
cannot be fixed forward at all: npm's suggestion is
`{ "name": "prisma", "version": "6.12.0", "isSemVerMajor": true }` — a
**downgrade** from the pinned `6.19.3`.

- `package-lock.json`: regenerated by `npm install --save-exact`.

### Task 2 — make the CI comment true, and give the census an owner

`.github/workflows/ci.yml:71-72` currently reads:

```
# Visible but non-blocking: the current high advisories live in
# next/vite themselves with no compatible fix released yet.
```

Both halves are false as of this measurement, and the second was false before
this branch touched anything:

- "live in next/vite themselves" — after the bump the high advisories live in
  `brace-expansion`, `browserslist`, `js-yaml`, `nanoid`, `@prisma/config`,
  `prisma` and `deepmerge-ts`. None is `next`. `vitest`'s own current advisory
  is **moderate**, so `--audit-level=high` does not even see it.
- "no compatible fix released yet" — seven of the twelve report
  `fixAvailable: true`.

Rewrite the comment to state the **policy only** — why the step is
`continue-on-error` — and link the census. Per CLAUDE.md's *Comment Discipline*,
a roster of which packages currently carry advisories is precisely a claim
reaching past the file it sits in: the edit that invalidates it happens in
`package-lock.json`, which the comment's author never sees. Name no packages and
no counts in the workflow.

The census goes in `docs/supply-chain.md`, which already owns dated measurements
and ships each with the command that re-derives it. Add a section carrying:

- the post-upgrade totals, whole-tree and `--omit=dev`, with the arithmetic;
- the re-derivation command, so the numbers are checkable rather than trusted;
- why the step does not block, and what would have to change for it to;
- the `prisma`-rooted trio and why it is the one group with no forward fix.

**Do not restate what the comment used to say** in either file. That
before-and-after belongs in the PR body (CLAUDE.md: *Comments state what is true
now*).

### Task 3 — the side effect the issue could not have predicted

16.3.4 adds `next dev` behaviour that 16.2.10 does not have: when it detects an
AI coding agent, it writes a managed block into `AGENTS.md`. It fired on the
first `npm run worktree:up` of this branch, and it is new — the module that does
it, `node_modules/next/dist/server/lib/generate-agent-files.js`, does not exist
in 16.2.10 at all.

The block's own text argues for committing it ("committing it with your work
keeps the tree clean"). Don't. There is a declarative opt-out —
`ensureAgentRulesForDev` is gated on `config.agentRules !== false`, and
`agentRules?: boolean` is a typed, schema-validated top-level `NextConfig` key
(`config-shared.d.ts:1574`, `config-schema.js:496`, `@default true`).

Take the opt-out and revert `AGENTS.md`. Committing the block would put a string
**Next owns** into a file whose claims this project maintains on purpose: any
patch release that rewords it re-dirties every tree, which is the
self-invalidating-claim shape CLAUDE.md's *Comment Discipline* exists to
prevent. One declarative line is smaller and does not churn.

Note for whoever revisits this: `writeAgentFiles` would have scaffolded
**both** `AGENTS.md` and `CLAUDE.md` had neither existed. `AGENTS.md` exists, so
it upserted there and skipped `CLAUDE.md` — this repo's `CLAUDE.md` was never
at risk, but that is a property of the tree, not a guarantee from Next.

**Prove the line bites.** Restart the worktree's dev server with
`agentRules: false` and confirm `AGENTS.md` stays clean; then remove the line,
restart, and confirm the block returns. A config key that compiles but changes
nothing certifies nothing. Restore afterwards and re-verify.

### Task 4 — verification

The acceptance criterion is "full CI green, e2e included", and singles out the
standalone build (`output: "standalone"`) because both the integration and e2e
jobs run against it.

Run in the worktree, against its own isolated app and database (`npm run
worktree:setup`, then `npm run worktree:up` — both tiers read
`INTEGRATION_BASE_URL` automatically):

1. `npm run typecheck`
2. `npm run lint`
3. `npx vitest run --project unit --project components`
4. `npx vitest run --project unit-sweeps --project integration`
5. `npm run build` — the standalone bundle
6. `npx playwright test`

Run 3 and 4 as separate invocations rather than `npm test`. `npm test` chains
them with `&&`, so one red unit test means the integration tier reports
*nothing* — not zero failures.

**Known, expected, and not a regression:** `eslint-config-next@16.3.4` adds
`@next/next/no-location-assign-relative-destination`, which flags **6 existing
call sites** across five components. They are warnings; `npm run lint` exits
**0** (measured, both before and after). CI's lint step passes. Whether to
convert those `window.location` calls to `useRouter().push()` is a separate
question about pre-existing code that this bump only made visible — it is not
this PR's to answer, and the PR body should say so rather than leave a reader
wondering whether the warnings are new breakage.
