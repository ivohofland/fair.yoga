# Node 24 LTS (#536) — implementation plan

**Goal:** move every Node pin from 22 to 24 LTS, stop Dependabot proposing
Node majors, and make CI prove the built images can load Prisma's engines.

**Direction agreed 2026-09-30:** Node 24 now (not 26 — no bundled Corepack,
which this repo's pnpm integrity gate depends on; not 25 — EOL 2026-06-01).
Dependabot ignores semver-major for `node` (docker) and `@types/node` (npm);
#716 and #152 are closed as superseded. A CI smoke step is added.

## Premise, as measured (not as the issue stated it)

## Task 2 — Dependabot ignores Node majors

Files: `.github/dependabot.yml`, `docs/supply-chain.md`.

1. `docker` entry: `ignore: [{dependency-name: node, update-types:
   [version-update:semver-major]}]`. Digest and minor/patch updates keep
   flowing.
2. `npm` entry: the same for `@types/node`. It tracks the runtime major, so it
   moves in the same deliberate PR as the image.
3. A comment on each ignore says why (odd majors are never LTS and are
   proposed anyway, as #716 did; Corepack leaves Node at 25; a runtime major
   is an issue, not a monthly PR). It does not name issue counts or list
   versions.
4. `docs/supply-chain.md` "Going forward" paragraph: currently says a bump
   past Node 25 arrives as a red CI run. Replace it with the new behaviour:
   majors are ignored, and digests still move.

Check: Dependabot has no local dry-run. Validate the file against
SchemaStore's `dependabot-2.0` JSON schema. If no validator runs cleanly, say
so in the PR rather than claim validation. The real proof comes after merge:
#716's successor stops appearing.

## Task 3 — CI proves the images load Prisma's engines

Files: `.github/workflows/ci.yml` (`docker-build` job), new
`scripts/ci/prisma-engine-probe.cjs`.

1. The probe script, piped over stdin into the runner image
   (`docker run --rm -i --entrypoint node fairyoga - < scripts/ci/…`, because
   the runner image does not contain `scripts/`). It constructs
   `PrismaClient` resolved from `/app` with datasource
   `postgresql://u:p@203.0.113.1:5432/none?connect_timeout=3` (RFC 5737; no
   real host can answer). Exit 0 only when `$connect()` fails with error code
   `P1001`. Any other outcome exits non-zero, printing the error: a require
   failure, an init error without that code, or an unexpected connect.
2. Migrate image: `docker run --rm -e DATABASE_URL=<same> fairyoga-migrate
   pnpm exec prisma migrate status`. That command exits 1 on P1001 as well,
   so the step asserts on its output: it passes only if the output contains
   `P1001`, and it echoes the output either way.
3. Update the job's header comment: it's no longer "nothing is pushed or
   run". Name what the run proves (the engine loads) and what it deliberately
   doesn't (no database).

**Prove both steps bite** (a scratch Dockerfile in the scratchpad; the real
one is never edited for this):
- Runner: delete the query engine library in the runner stage (`RUN rm
  /app/node_modules/.pnpm/@prisma+client*/node_modules/.prisma/client/libquery_engine-*`).
  Build it, run the probe, and require a non-zero exit. Record the error text.
- Migrate: remove libssl from the image (`RUN apk del --no-cache libssl3` or
  equivalent). Build it, run the migrate step, require failure without
  `P1001`. Record the text.
- Restore by deleting the scratch file, re-run both steps against the real
  images, require a pass, and end with `git status` clean apart from the
  intended edits.
